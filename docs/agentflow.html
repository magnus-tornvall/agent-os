Agentflow Field Guide

Agentflow is a compiled binary that takes a GitHub issue number and, without anyone watching, drives it through four fresh agents in a throwaway git worktree until a pull request is open, reviewed, fixed and judged against what the issue actually asked for.

$ agentflow 42

Everyday detail is open; contracts, exact signals and source pointers stay folded until you ask.

The four load-bearing ideas

Everything else in this guide is a consequence of one of them.

The driver owns the forge; the agents own the codeboundary

Claiming the issue, opening the pull request and pushing are done by the binary, never by an agent. Two exceptions were bought deliberately: the reviewer posts its own findings, and the conformance judge posts its own verdict — because a driver that renders comments has to parse them back out of an agent first.

The prohibition on the other two phases lives in their prompts, not in code. Nothing stops an agent running gh. It is a budget, not a fence.

Every phase is a fresh agentstructural

Sandcastle's resumeSession is incompatible with more than one iteration, so each phase starts with no memory of the last. The reviewer genuinely did not write the code it is reviewing, and the conformance judge has read neither the implementation transcript nor the review's reasoning — only what landed on the branch and what was said on the pull request.

The cost is that every prompt must stand alone. The benefit is the only honest review an unattended pipeline can produce.

Commits are the only gategate

After the implement phase the binary asks one question: did that agent leave commits on the branch? If not, no pull request is opened and the run stops. There is no build, no test run, no lint, no frontmatter check — nothing that would need the binary to know anything about the repository it is driving.

It refuses rather than resumesrecovery

Six checks run before anything is mutated. If the branch exists, a pull request is open, or the issue is closed or someone else's, the run refuses and nothing has happened yet. There is no state file, no resume flag and no crash recovery: delete the branch and run it again.

How each rule is actually enforcedhonest answer

Two mechanisms, and only one of them is a mechanism.

Enforced by construction: agents cannot push, because the driver holds the only git push calls and runs them from the worktree between phases. Agents cannot see each other's reasoning, because each phase is a new process.

Enforced by prose: every ✕ in the table above. Each prompt opens with an explicit prohibition — Do not touch GitHub. No gh, no comment, no reply — and the agent runs on the host with bypassPermissions, so nothing but the instruction stands between it and the forge.

This was a deliberate trade. When the driver rendered the comments, "no agent calls gh" was auditable with one grep of a log. Letting the reviewer post directly deleted a findings file, a schema, a read-back path and a whole contract — and spent that audit line to do it.

What you control

Three levers, in descending order of power: the prompts, the per-phase settings in agentflow.toml, and the branch you happen to be standing on.

Lever 1 — the prompts

The largest surface by far. Four markdown files; the binary reads them and never inspects them.

Each phase's prompt key is the only required setting in the file. The path resolves against the config file that declares it, expands ~, and passes absolute paths through — so one prompt set can be shared across every repository you drive, and a repository can point at prompts that do not live inside it.

All four are read and checked at startup, before the issue is claimed, so a typo in a path fails while nothing has happened yet.

Sandcastle adds SOURCE_BRANCH and TARGET_BRANCH to every prompt itself; passing either one yourself is an error. The sets above are compiled in — a repository cannot add an argument, and a prompt that references an unknown key gets no substitution.

ISSUE_URL and PR_URL are passed but unused by the prompts shipped in this repository. They are there for yours.

Pulling live context into a promptsandcastle

A prompt file may contain shell expressions, which sandcastle runs on the host and replaces with their stdout before the agent sees the prompt. This is how the fix phase gets the review's findings without a line of driver code:

!`gh pr view {{PR_NUMBER}} --json comments --jq '.comments[] | "### @\(.author.login)\n\n\(.body)\n"'`

Argument substitution runs first, expansion second — so {{PR_NUMBER}} inside the command is already resolved. Expansion only applies to expressions written in the prompt file; the same pattern arriving inside an argument value (an issue body, say) is inert text.

Lever 2 — agentflow.toml

One file, in the root of the repository being driven. No layering, no user-level file, no environment defaults, no --config flag.

copyToWorktree = []

[phases.implement]
prompt = "workflows/prompts/implement.md"
maxIterations = 1

[phases.review]
prompt = "workflows/prompts/review.md"

[phases.fix]
prompt = "workflows/prompts/fix.md"

[phases.conform]
prompt = "workflows/prompts/conform.md"

All four phase tables are required even when you only set a prompt path. Any key the validator does not recognise — including a misspelling of an optional one — fails the run with the list of keys that are valid there.

Change one here and you must change it in the prompt too — nothing checks that they agree, deliberately: a grep passes on a prompt that merely mentions the line and fails on one that assembles it, so it would report confidently in both wrong directions.

Why the iteration count is the interesting knobtuning

An iteration is a whole agent run. The loop stops early the moment the completion signal appears in the output, so maxIterations is a ceiling on retries, not a schedule — the defaults exist because a first pass sometimes ends without printing the line.

conform defaults to a single iteration against review's two, and that asymmetry is deliberate: it makes exactly one append-only comment, so a second attempt cannot recover a partial post but can very easily duplicate a complete one.

Setting a phase to 0 is how a repository omits it; there is no separate flag. A skipped phase returns no signal and no commits, which the driver's existing gates report without ever knowing it was skipped.

Lever 3 — where you are standing

There is no --repo flag and no --base flag. The invocation directory decides everything.

The repository is the one containing your current directory, found with git rev-parse --show-toplevel. The base branch is whatever that repository has checked out when you invoke — so targeting a different base is git switch, and targeting a different repository is cd.

The branch it creates is always agent/issue-<n>, and the remote is always origin. Neither is configurable: a recognisable branch name across every repository is the point, and three other assumptions rest on the remote's name.

What you deliberately cannot control

Each of these was argued and closed. The reasons differ.

The agent kindSandcastle's six agent factories have genuinely different option shapes, including three incompatible effort unions. effort would become valid or invalid depending on a sibling key.

How it ends

Five words. The last line of output is done: <word>, and the exit code is read straight off it.

clean-reviewexit 0The reviewer found nothing, and the conformance judgement is on the pull request. Ready for you.
fixedexit 0Findings were posted, answered, and pushed; the conformance judgement is on the pull request.
no-commitsexit 1The implement phase left the branch untouched. No pull request was opened.
review-inconclusiveexit 1The reviewer printed neither signal, so whether findings were posted is unknown. The pull request is open and needs a human.
conform-inconclusiveexit 1Everything before it succeeded, but whether a scope judgement reached the pull request is unknown.
Why an unknown signal stops the run instead of guessingrationale

The two review signals are the only thing the driver reads out of that phase. If neither fires, the reviewer may have posted five findings, or none, and the log is the only place the answer exists.

Running the fix phase on that guess is worse than not running it: on a clean review it invents work, and on a posted set it silently half-applies one. So the run stops with the pull request open — which is a state a human can read in ten seconds.

A failure the binary throws — a refusal, a missing prompt, a gh error — prints agentflow: <message> to stderr and exits 1 without an outcome word.

The one outcome that is currently wrongknown

A run whose fix phase is configured to maxIterations = 0, or whose fixer rejected every finding, still reports fixed with no commits. It earns a sixth word when someone actually configures a run that way and has to read the result.

Sharp edges

Things that are true, not bugs — but that will surprise you once each.

host The agents are not sandboxed

Sandcastle requires a sandbox provider and agentflow passes noSandbox(), which runs the agent as a local process against a bind-mounted worktree. Because noSandbox() declines to pass --dangerously-skip-permissions, the grant rides on the agent instead: permissionMode: "bypassPermissions", a literal in the binary.

What is isolated is the working tree, not the machine. Four unattended agents run on your host with full tool access for the length of the run. Docker and podman providers exist in sandcastle and are a deliberate deferral — they return when a target repository needs an environment the host cannot provide.

host Nothing stops an agent calling gh

Two phases are told not to touch GitHub and two are told to make exactly one kind of call. All four could do anything your gh credentials allow. The prompts are the whole control.

run The claim is not reverted when a run fails

The issue is assigned to you immediately after the six refusal checks pass and before the worktree exists. Nothing un-assigns it if a later phase throws. Reverting a claim is an explicit deferral, on the grounds that a binary which half-recovers is worse than one that refuses.

run Recovery is one line, and you have to know it

Because the run refuses when the branch or pull request already exists, re-running after a failure means clearing both:

git branch -D agent/issue-42
git push origin --delete agent/issue-42
agentflow 42

If the worktree was dirty when the run ended, it is preserved on disk instead of removed, and the path is printed. Nothing cleans it up for you.

run The base branch must already be on origin

This is the first of the six refusals and it exists for one reason: gh pr create against a local-only base fails late and confusingly, after the issue has been claimed and the whole implement phase has run.

note Nothing coordinates two runs at once

No lock, no PID file, no queue. Structurally, distinct issues get distinct branches, worktrees and log filenames, so they do not collide. The residual hazard is two unsandboxed agents on one machine at the same time — which belongs to the sandbox question above, not to a lock.

note The logs are the only per-run evidence, and they are not committed

Each phase drains to .sandcastle/logs/issue-<n>-<timestamp>-<phase>.log in the repository being driven, and .sandcastle/ is gitignored. There is no JSONL run record of timings, iterations and signals — that existed to evaluate the sandcastle stack and was removed when the evaluation ended. Commit shas are in git; everything else is in those files, on that machine.

Open and closed

Absent features come in two kinds, and the difference matters more than the list. A deferral is waiting for a trigger. A boundary was argued and closed — reopening it means reopening the argument.

Deferrals

Each one names the thing that brings it back.

Other forges — Azure DevOps, self-hosted
The plumbing was already proven by hand; what is unproven is the stage shape. The Azure DevOps implementation is the change that should create the forge seam, with the shape it actually needs — thread-based review comments rather than issue comments. Until then there is no forge abstraction at all, on purpose.
Docker or podman sandboxing
Keeps out the image lifecycle, mount configuration and .sandcastle/.env handling. Returns when a target repository needs an environment the host cannot provide.
Resume, state files, crash recovery, reverting a claim
A run refuses when the branch or pull request exists, which leaves a one-line recovery. A binary that half-resumes is worse than one that refuses.
A per-run record of timings, iterations and signals
It existed to evaluate the sandcastle stack, and that evaluation is over. Reinstate if runs ever need comparing across repositories.
Driver-owned comment posting, a findings file, structured output
The reviewing agent posts, accepting transient errors and format drift for a simpler pipeline. Reinstate if public mis-posts or half-commented pull requests actually occur — only a driver-read artifact can be validated before anything is published.
Configuration as an imported TypeScript module
A compiled binary can import TypeScript from disk, so this is a choice rather than a limit. With the phase sequence fixed, code buys only a route to reintroduce logic one repository at a time. Returns with the first repository that needs a phase the fixed pipeline does not have.
A host notification when a run completes
The pull request is the outcome and GitHub already notifies on it. It was also the binary's only platform-specific code path.
Tests for the configuration surface
Verified by running the binary. Deferred against the argument that unknown-key rejection has no observable behaviour other than its error text.

Boundaries

Closed on an argument about layering, not about timing.

Write fencing — policing which paths an agent may touch
The pull request diff is the check, and the conformance phase reports every unrequested change by location. A driver that polices paths polices the wrong layer.
Configuration layering, a user-level file, environment defaults
With inheritance, what a run will do in a repository stops being answerable from that repository. Duplicated prompt paths across several short config files are legible; one inherited file is not.
An agentflow init command or embedded default prompts
It reinstates target-repository scaffolding that was already killed once, and bakes one review standard into a build artifact for every repository.
A commands block in config, or a required project CLAUDE.md
Commands in config assert facts about repositories that drift the moment a script is renamed; a required CLAUDE.md makes the tool unusable in a repository until someone writes one. The prompts already tell the agent to read the convention the repository visibly follows.
An agent-judged actionability gate on the issue
Judging whether an issue is actionable needs an agent, which is a fifth phase, which reopens the fixed pipeline. Validation stays mechanical: open, and not assigned to someone else.
Concurrency control — a lock, a PID file, a queue
Nothing structural collides. The residual hazard belongs to the sandbox deferral.
Checking that a phase's signal appears in its prompt
The check worth having is not the check available. A literal grep passes on a prompt that mentions the signal in prose and fails on one that assembles the line.
--print-config or --dry-run
The run already states what every phase resolved to, in output it produces anyway, without a second entry point.
Warning-level, non-fatal configuration diagnostics
The first non-fatal message makes config failure a two-tier thing where today it is one.
A --repo flag
cd reaches the same outcome, and the flag was the only reason repository resolution would have two sources that can disagree. Reinstate if something other than a human shell ever invokes it.

What sandcastle provides, and what agentflow addsdependency

@ai-hero/sandcastle is agentflow's one dependency. It contributes four things:

The worktree. createWorktree makes a real git worktree on a named branch off a named base, under .sandcastle/worktrees/, and hands back a handle that runs agents in it and tears it down — preserving it if it is dirty.

The agent loop. worktree.run() executes an agent up to maxIterations times, watching its output for any of the completion signals, and reports back the iterations, the commits the agent made, the signal that matched, and where the log went.

Prompt assembly. {{KEY}} substitution from promptArgs, two built-in branch arguments, and host shell expansion of !`command` expressions.

Providers. claudeCode(model, {effort, permissionMode}) for the agent, and a choice of sandbox — of which agentflow uses exactly one, noSandbox().

Everything else is agentflow: the phase sequence, the configuration file and its validator, the six refusals, the commits gate, the branching on review's two signals, every gh call the driver makes, and the outcome vocabulary.
